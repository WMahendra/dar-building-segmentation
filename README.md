# Building footprint segmentation under class imbalance — Dar es Salaam

Mapping buildings in rapidly growing, largely unplanned African cities is a
prerequisite for disaster risk modelling, service planning and population
estimation — and in most of these cities no authoritative building register
exists. Drone and satellite imagery can fill the gap, but the task has a
structural difficulty that is easy to report your way around: buildings occupy
only a small fraction of the pixels. A model that predicts "no building"
everywhere scores well on overall accuracy while being useless.

**This repository asks a narrow, answerable question: which way of handling that
imbalance actually buys you recall on the building class, and what does each one
cost in precision?** Eight segmentation arms and three pixel-based comparators
are trained under identical conditions, and evaluated on a scene no arm has
seen.

## Data

| | |
| --- | --- |
| **Source** | [Open Cities AI Challenge Dataset](https://source.coop/open-cities), GFDRR Labs / World Bank |
| **Scenes** | 6 drone mosaics over Dar es Salaam, Tanzania (tier 1) |
| **Imagery** | RGB, sub-metre, CC BY 4.0 |
| **Labels** | OpenStreetMap building footprints, ODbL-1.0 — 8,466 buildings in scene `a017f9` alone |
| **Access** | Fully open, no account or credentials |

The dataset is discovered through its STAC catalogue rather than hard-coded
paths, so `--city znz` or `--city acc` runs the same experiment over Zanzibar or
Accra without touching the code.

See [DATA.md](DATA.md) for the licence terms and the required citation. The two
licences are **not** the same and the imagery and labels cannot be redistributed
under a single one.

**What the labels are, precisely.** These are building footprints, not
informal-settlement boundaries. The methodological lineage here is the
fully-convolutional work on informal settlement detection (Persello & Stein,
2017), and these neighbourhoods are largely unplanned, but the target being
predicted in this repository is *building / not building*. That distinction is
stated here because conflating the two would misdescribe what the metrics mean.

## Method

**Split.** Whole scenes go to one split only — 4 train, 1 validation, 1 test.
Neighbouring patches from a single flight overlap in content and share
radiometry, so a random patch split leaks the test set into training and inflates
every metric. The split is deterministic, not random, so it is identical on
every machine.

**Model.** One U-Net, fixed across all arms. If the architecture moved between
arms, a difference in recall could not be attributed to the treatment. The final
layer's bias is initialised to the measured log-odds of the positive class, so
training starts at the correct base rate instead of spending its first epochs
unlearning a confident wrong prior.

**The two levers**, varied one at a time and then crossed:

| | arms |
| --- | --- |
| **Loss function** | `bce` (control), `weighted_bce`, `dice`, `tversky` (β = 0.7), `focal`, `bce_dice` |
| **Sampling** | `oversample` — half of every batch contains buildings |
| **Both** | `oversample_dice` |

`weighted_bce`'s positive weight is the inverse class frequency *measured* from
the data in preprocessing, not a hand-picked number.

**Pixel-based comparators.** `pixel_plain`, `pixel_smote`,
`pixel_smote_adaboost` — boosted trees on RGB plus local standard deviation and
gradient magnitude at two scales. These answer a different question: how much of
the task is solvable with no spatial context at all? They are given real texture
features rather than bare RGB, because beating a straw man would prove nothing.
SMOTE is applied to training pixels only; resampling before the split is the
commonest way an imbalance experiment is quietly invalidated.

**Metrics.** Overall accuracy is not reported anywhere in this project — on a
class occupying a few percent of pixels it would rank the worst model first.
Reported instead: IoU and F1 on the building class, precision and recall
separately, and average precision as a threshold-free summary. Confusion counts
are swept across thresholds in a single pass, so the curves and the headline
numbers come from the same counts. Mosaic collar pixels are excluded from the
metrics, so background is not inflated by flight geometry.

## Reproducing

```bash
pip install -r requirements.txt

python -m src.fetch_data --dry-run        # what will be downloaded, and how big
python -m src.fetch_data                  # 6 Dar es Salaam scenes + labels
python -m src.preprocess --city dar       # rasterise labels, index tiles, measure balance

python -m src.train --all                 # the eight segmentation arms
python -m src.baseline_pixel --all        # the three pixel comparators
python -m src.figures                     # results table + figures
```

`notebooks/01_run_colab.ipynb` runs the same pipeline on a Colab GPU.

Every run records the settings it used. If a results directory ends up mixing
arms trained under different settings, `src/figures.py` says so rather than
printing a table that silently is not a like-for-like comparison.

## What is verified, and what is not

The pipeline is exercised end to end against synthetic fixtures
(`tests/make_synthetic.py`) that match the real data structurally — uint8 RGB +
alpha GeoTIFFs in a projected CRS, a transparent mosaic collar, polygon
footprints, and a 5.8% positive class. Confirmed on those fixtures: tiling and
collar exclusion, label rasterisation and alignment, each loss producing a
distinct optimisation trajectory, the model learning (AP 0.97 for `dice`, 0.91
for `bce`), georeferenced prediction rasters, the metric sweep, and every figure
rendering.

Those fixture numbers say **nothing** about building detection — they are
synthetic rectangles, and the pixel baselines solve them almost perfectly, which
real imagery will not allow. They establish only that the code is correct.
